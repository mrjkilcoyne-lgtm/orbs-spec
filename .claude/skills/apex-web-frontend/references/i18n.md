# Internationalization (i18n)

## Scope
Building software for multiple languages, scripts, and locales: text, formatting, layout, and process.

## Core principles
- i18n is architecture, l10n is content: externalize strings and locale logic from day one; retrofitting is a rewrite.
- Text expands (German +35%) and reflows (CJK, Thai no spaces): layouts must flex; truncation is a design failure.
- Never concatenate translated fragments: grammar reorders sentences; use full-sentence templates with named placeholders.
- Plurals are not "s": languages have 1-6 plural forms; use ICU MessageFormat/CLDR rules, never if(count>1).
- Locale ≠ language: dates, numbers, currency, collation, and first day of week vary within a language — use Intl APIs, never hand-format.

## Apex practices
- RTL from the start: logical CSS properties (inline-start), dir attribute, mirrored iconography where meaning flips.
- Keys with context for translators (screenshots, descriptions); pseudo-localization in CI catches hardcoded strings and overflow.
- Unicode correctness: normalize (NFC), grapheme-aware truncation, locale-aware case mapping (Turkish i).
- Treat translations as a deployment artifact with fallback chains (fr-CA → fr → source).

## Pitfalls
- String concatenation and variable-order assumptions breaking half the languages.
- Flags as language icons (flags are countries, not languages).
- Encoding dates as MM/DD strings anywhere near a user.

## Tools & references
ICU MessageFormat, ECMA-402 Intl, CLDR, FormatJS/i18next/Fluent, pseudo-localization tooling.
