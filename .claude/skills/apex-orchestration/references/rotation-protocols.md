# Rotation Protocols

## Scope
Cycling lenses across iterations, reviews, and calendar time so no single perspective calcifies into the only perspective.

## Core principles
- Author-lens ≠ review-lens is the prime rotation rule: work authored under a domain lens gets reviewed under blindspots plus a *different* domain-adjacent lens (the API designed with backend lenses gets reviewed with human-factors and security lenses). The author's lens can only find the defects it already knows about — that's what makes it a lens.
- Iteration rotation fights anchoring: on v2 of anything, swap the lead lens (v1 led by function → v2 led by form; v1 led by structure → v2 led by content). The first draft anchors its own revisions; a rotated lens is the structural escape (see blindspots/anchoring).
- Temporal rotation keeps breadth alive: a standing cadence where recurring work cycles through lens families (this sprint's refactor reviewed for performance, next sprint's for security, the third for accessibility) — coverage through rotation rather than exhaustion, the same logic as crop rotation.
- Rotation is how skills stay sharp: an unused lens degrades into a bullet list; scheduled rotation (the "lens of the week" applied to real work) is spaced repetition for judgment — the personal-effectiveness spaced-repetition principle applied to the skill system itself.
- Rotate the *level*, not just the domain: zoom rotation (one pass at architecture altitude, one at code altitude, one at user altitude) catches the classic altitude bugs — perfect code in the wrong module, perfect module in the wrong product.

## Apex practices
- Bake rotation into the workflow, not memory: PR templates or review checklists that name this cycle's check-lens; the conductor assigns reviewer lenses explicitly when orchestrating.
- Run the three-altitude pass on anything significant: does it work (code altitude)? does it fit (system altitude)? does it matter (user/business altitude)? — three quick passes beat one blended stare.
- When stuck, force a random rotation: pick a genuinely foreign lens (queueing-theory on a UX flow, storytelling on an architecture doc, mondrian on a schema) — foreign lenses generate the questions familiar ones can't (the recasting exercise from the atelier).
- Track which lenses found last quarter's real defects and re-weight the rotation toward them — rotation with a scoreboard, not ritual.

## Pitfalls
- Fake rotation: the same person applying the "different lens" they already agree with — rotation works best when it changes the checklist actually executed, ideally the agent/person too.
- Rotation without residency: switching lenses so fast nothing is applied deeply — each lens gets a full pass, not a glance.
- Rotating out the lens that keeps finding problems because it keeps finding problems.

## Tools & references
Review checklists with named lenses, the skeptic agent (institutionalized rotation), de Bono's Six Thinking Hats (the ancestor protocol), crop-rotation as the mental model.
