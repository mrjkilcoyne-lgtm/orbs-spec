# Support Content

## Scope
Help articles and FAQs that reduce support tickets: clarity, problem-solution structure, and rapid search discoverability.

## Core principles
- Support content is written by experts answering novices; explain every term and assumption. What's obvious to the support team is a mystery to customers.
- Problem-first structure: state the problem or error message first, then solution. Customers search by the problem they see, not the feature name.
- FAQ (Frequently Asked Questions) is a misnomer; they're rarely questions customers ask but rather edge cases staff anticipate. Title them as problems ("Resetting your password") not questions.
- Completeness is coverage of all user types and skill levels; a guide on "changing settings" should work for power users and novices alike. Provide screenshots.
- Keep support content current; outdated help drives customers to social media and reviews, where they amplify complaints.

## Apex practices
- Structure help articles as: Problem statement → Symptoms (how does the user know this is happening?) → Solution (step-by-step) → Prevention (if applicable).
- Use tags (category, skill level, product version) to filter and organize; customers should find help by searching.
- Link to related articles at the bottom; "Did this solve your problem? No? Try this article..."
- Measure: which articles get views? Which get "was this helpful?" feedback as negative? Fix low-performing articles.

## Pitfalls
- Writing from the product's perspective ("This feature allows you to...") instead of the customer's problem ("When X goes wrong, do Y").
- Overly formal or technical language; a support article for all users should avoid jargon.
- Deleting outdated content without redirects; broken links frustrate customers.

## Tools & references
Zendesk / Intercom / Help Scout (platforms), customer support metrics (first-response time, resolution rate), search analytics.
