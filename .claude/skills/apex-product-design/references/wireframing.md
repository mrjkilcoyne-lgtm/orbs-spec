# Wireframing

## Scope
Low-fidelity layouts: structure, flows, interactions, and communication with stakeholders and developers.

## Core principles
- Wireframes strip visual design and show structure: where elements go, content hierarchy, primary vs secondary actions — low fidelity speeds iteration and focuses on layout, not pixels.
- Wireframe fidelity should match the decision: rough sketches for brainstorming, mid-fidelity for decisions, high-fidelity (annotated mockups) for handoff to developers.
- Flows (user journeys) in wireframes show sequences: happy path, edge cases, error paths — missing edge cases lead to incomplete designs and rework.
- Annotations (labels, notes, interactions) make wireframes unambiguous; devs shouldn't guess what a section is for or how an element behaves.
- Wireframes should be quickly testable with users; even rough wireframes reveal navigation problems and content gaps before design polish.

## Apex practices
- Start with rapid sketching (paper, whiteboard) to explore layouts; formalize in Figma only after exploring 3–5 options.
- Create templates (header, footer, cards) for consistency and speed; reuse them across screens.
- Annotate with data examples, error states, and interactions; don't leave implementation details to interpretation.
- Test wireframes with users before visual design; discovering IA problems after visual polish is expensive.

## Pitfalls
- Over-designing wireframes; they look good but the structure is wrong, then polish is wasted.
- Wireframes that ignore responsive constraints; designing for desktop only, then "adapting" to mobile, usually breaks mobile UX.
- Not showing edge cases (empty states, loading, errors) — devs ship without these, harming UX.

## Tools & references
Figma, Balsamiq, Miro, wireframing templates; "Web Design for Non-Designers" (Young); information architecture practices for structure.
